# 상세 설계 스킬 (A-SPICE SWE.3)

공통 위치와 ID 규칙은 프로젝트 루트 `CLAUDE.md`를 따른다. 입력은 확정된 아키텍처다.

## 1. 필수 규칙

1. **컴포넌트를 모듈(`DD-M-nnn`)로 분해한다.** 모듈마다 책임(한 문장), 소속 컴포넌트(`ARCH-C-`), 할당 요구사항을 기록한다.
2. **특정 수준 이상의 모듈은 인터페이스를 반드시 정의한다.**
3. **인터페이스가 정의된 모듈은 오직 그 인터페이스를 통해서만 통신한다.** 다른 모듈의 내부 함수·데이터 직접 접근 금지.
4. **클린코드 원칙을 준수한다.**
5. **단일 책임 원칙(SRP)을 준수한다.**

### "특정 수준"의 기준

프로젝트가 기준을 정해 `CLAUDE.md`에 적어 두었다면 그것을 따른다. 없으면 기본값으로 다음 중 하나라도 해당하는 모듈은 "인터페이스 정의 대상"으로 본다.

- 다른 모듈 두 개 이상이 사용한다.
- 컴포넌트 경계를 넘는 호출을 처리한다 (아키텍처 인터페이스 `ARCH-I-`의 구현 모듈).
- 외부 자원(하드웨어, 파일, 네트워크, OS)을 감싼다.

> 이 기본값은 스킬 작성자의 가정이다. 팀 기준이 있으면 반드시 교체한다.

대상이 아닌 모듈(파일 내부 보조 모듈 등)은 인터페이스 없이 정의해도 되지만, 비공개(`static`)로 유지하고 외부에서 참조하지 못하게 한다.

## 2. 모듈 상세 설계 항목

- 모듈 ID, 책임, 소속 컴포넌트, 할당 요구사항
- 공개 인터페이스(`DD-I-nnn`) — 대상 모듈만: 함수 시그니처, 인자(타입/범위/단위/방향), 반환값(정상/오류 값 의미), 사전·사후조건, 오류 처리
- 내부 데이터 구조와 상태, 불변식
- 함수별 동작: 처리 절차(의사코드 또는 순서도/상태도), 분기 조건, 오류 경로
- 함수 단위로 단위 테스트가 가능한 크기와 책임인지 확인한 결과
- 의존하는 다른 모듈의 인터페이스 목록 (구현이 아니라 인터페이스에 의존)

함수는 **반환값을 가진다**는 구현 규칙(`implementation` 스킬)과 맞도록, 설계 단계에서 모든 함수의 정상/오류 반환값을 정의한다. 반환할 값이 없는 동작도 "성공/실패 상태 값"을 정의한다.

## 3. 클린코드·SRP 적용 기준 (설계 수준)

- 이름이 의도를 드러낸다 (약어, 중의적 이름 금지). 모듈·함수 이름은 책임을 설명한다.
- 함수는 한 가지 일만 한다. 설명에 "그리고"가 들어가면 분리한다.
- 함수는 작게: **순환복잡도 10 이하, 80라인 이하**(Lizard 기준, `CLAUDE.md` 2.3절)를 설계 단계부터 지킨다. 분기가 많은 동작은 설계에서 작은 함수로 나눈다. 추상화 수준을 한 함수 안에서 섞지 않는다.
- MC/DC 측정이 가능하도록 하나의 결정(조건식)에 들어가는 조건은 6개 이하로 설계한다.
- 인자는 적게 (가능하면 3개 이하), 플래그 인자·출력 인자 남용 금지, 구조체로 묶을 수 있으면 묶는다.
- 부수효과를 숨기지 않는다. 이름과 문서에 드러낸다.
- 중복 제거(DRY), 매직 넘버 대신 이름 있는 상수.
- 주석으로 나쁜 코드를 설명하지 않는다. 주석은 "왜"와 계약(Doxygen)에 사용한다.
- 오류 처리는 정의된 반환값 체계로 일관되게 한다.
- SRP: 모듈은 변경 이유가 하나다. 변경 이유가 둘 이상이면 분리한다.

## 4. 추적성

- 아키텍처 컴포넌트/인터페이스 ↔ 모듈/인터페이스 ↔ (이후) 소스 코드·단위 테스트를 양방향으로 `docs/traceability/trace-matrix.md`에 기록한다.
- 모든 모듈은 요구사항까지 거슬러 올라갈 수 있어야 하고, 모든 요구사항은 모듈로 내려갈 수 있어야 한다.

## 5. 절차

1. 컴포넌트 단위로 모듈 분해 (책임 중심)
2. 인터페이스 정의 대상 판정 (1절)
3. 인터페이스 정의, 의존을 인터페이스로 제한
4. 모듈·함수 동작 설계 (2절)
5. 클린코드/SRP 점검 (3절)
6. 추적 매트릭스 갱신
7. `review` 스킬로 상세 설계 체크리스트 리뷰
