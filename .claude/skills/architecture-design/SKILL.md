# 아키텍처 설계 스킬 (A-SPICE SWE.2)

공통 위치와 ID 규칙은 프로젝트 루트 `CLAUDE.md`를 따른다. 입력은 확정된(리뷰 완료) 요구사항이다.

## 1. 필수 규칙

1. **컴포넌트를 정의한다.** 컴포넌트마다 ID(`ARCH-C-nnn`), 책임(한 문장), 할당된 요구사항(`REQ-`)을 기록한다.
2. **모든 컴포넌트의 인터페이스를 반드시 정의한다.** 인터페이스 없는 컴포넌트는 허용하지 않는다.
3. **컴포넌트 간 통신은 오직 인터페이스를 통해서만 한다.** 다른 컴포넌트의 내부 데이터·함수·파일에 직접 접근하는 의존은 설계에 존재해서는 안 된다. 전역 변수 공유, 내부 헤더 include, 구현 클래스 직접 참조를 금지한다.
4. **응집도는 높이고 결합도는 낮춘다.**
5. **모듈화, 캡슐화, SOLID 원칙을 준수한다.**

## 2. 인터페이스 정의 항목

인터페이스(`ARCH-I-nnn`)마다 다음을 기록한다.

- 제공 컴포넌트(provider)와 사용 컴포넌트(consumer)
- 동작/함수 시그니처: 이름, 인자(타입, 방향 in/out, 단위, 범위), 반환값(정상/오류 값의 의미)
- 사전조건·사후조건·불변식
- 오류 처리 방식과 오류 코드
- 호출 순서·타이밍·스레드 안전성·자원 소유권(메모리 소유자)
- 데이터 형식과 버전
- 할당된 요구사항(`REQ-`)

## 3. 설계 원칙 적용 방법

### 응집도/결합도
- 컴포넌트의 책임이 한 문장으로 설명되지 않으면 쪼갠다 (낮은 응집도 신호).
- 의존 방향은 비순환으로 유지한다. 순환 의존이 있으면 인터페이스 추출 또는 의존 역전으로 끊는다.
- 의존은 구체 구현이 아니라 인터페이스(추상)에 한다.
- 데이터 결합(필요한 값만 전달)을 선호하고, 공통/제어/내용 결합은 제거한다.

### SOLID (컴포넌트 수준 해석)
- **S** 단일 책임: 컴포넌트는 변경 이유가 하나다.
- **O** 개방-폐쇄: 확장은 새 구현 추가로, 기존 인터페이스 수정 없이.
- **L** 리스코프 치환: 같은 인터페이스의 구현은 계약(사전/사후조건)을 지키며 서로 교체 가능해야 한다.
- **I** 인터페이스 분리: 소비자가 쓰지 않는 동작을 강제하는 비대한 인터페이스를 만들지 않는다.
- **D** 의존 역전: 상위 정책 컴포넌트가 하위 구현에 의존하지 않고, 둘 다 인터페이스에 의존한다.

### 모듈화·캡슐화
- 내부 상태와 구현 세부는 컴포넌트 안에 숨기고 공개 인터페이스만 노출한다.
- 공개 헤더(인터페이스)와 비공개 소스를 물리적으로 분리하도록 디렉터리 구조를 설계에 포함한다.

## 4. 동적 거동·자원

- 컴포넌트 간 주요 시나리오의 상호작용(시퀀스)을 기술한다.
- 동시성(태스크/스레드), 자원 사용(메모리, CPU 등), 오류·복구 전략을 기술한다.
- 품질 요구사항(`REQ-Q-`)과 제약사항(`REQ-C-`)이 설계 결정에 어떻게 반영됐는지 기록한다.
- 설계 결정은 대안, 선택 이유, 트레이드오프를 함께 남긴다.

## 5. 추적성

- 요구사항 ↔ 컴포넌트/인터페이스(양방향)를 `docs/traceability/trace-matrix.md`에 기록한다.
- 컴포넌트에 할당되지 않은 요구사항, 요구사항에 근거가 없는 컴포넌트가 없어야 한다.
- 통합 테스트 대상이 되는 인터페이스와 컴포넌트 간 연동 시나리오를 식별해 둔다.

## 6. 절차

1. 요구사항 확인 → 컴포넌트 후보 도출 (책임 중심)
2. 의존 관계 그림·표 작성, 순환·직접 접근 여부 점검
3. 인터페이스 정의 (2절)
4. 원칙 점검 (3절)
5. 동적 거동·자원·결정 기록 (4절)
6. 추적 매트릭스 갱신 (5절)
7. `review` 스킬로 아키텍처 체크리스트 리뷰
