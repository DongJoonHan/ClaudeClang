# 요구사항 분석 스킬 (A-SPICE SWE.1)

공통 위치와 ID 규칙은 프로젝트 루트 `CLAUDE.md`의 "산출물 위치와 ID 규칙"을 따른다.

## 1. 분류 규칙

모든 요구사항은 아래 중 정확히 하나로 분류한다.

| 구분 | ID 접두 | 설명 |
|---|---|---|
| 기능 요구사항 | `REQ-F-` | 시스템이 수행해야 하는 동작. 입력·처리·출력·조건이 드러나야 한다. |
| 품질 요구사항 | `REQ-Q-` | ISO 25010 품질 특성으로 기술한다 (아래 3절). |
| 제한 | `REQ-L-` | 시스템이 지원하지 않거나 보장하지 않는 범위·한계 (예: 최대 동시 접속 수). |
| 제약사항 | `REQ-C-` | 설계·구현 선택을 제약하는 외부 조건 (예: 언어, 표준, 플랫폼, 법규). |

> 제한과 제약사항의 구분은 이 스킬의 해석이다. 프로젝트에서 다르게 정의하면 `CLAUDE.md`에 적고 그것을 따른다.

### 기능 안전 요구사항은 별도 문서

기능 안전 요구사항(ISO 26262 등)은 이 문서에 섞지 않고 `docs/safety/safety-requirements.md`에서 관리한다 (ID 접두 `REQ-S-`).
- 일반 요구사항 문서에는 안전 요구사항 본문을 쓰지 않는다. 관련된 일반 요구사항에서 `REQ-S-xxx`를 참조(링크)만 한다.
- 안전 요구사항도 추적성 대상이다. 추적 매트릭스에 포함한다.

## 2. 요구사항 작성 품질 기준

각 요구사항은 다음을 만족해야 한다.
- 한 문장에 하나의 요구 ("그리고/또는"으로 여러 요구를 묶지 않는다).
- "shall/해야 한다" 형식, 능동태, 주체 명시.
- 검증 가능: 측정 기준·허용 오차·조건이 있어야 한다. "빠르게", "적절히" 같은 모호어 금지.
- 고유 ID, 출처(이해관계자 요구 또는 상위 문서), 우선순위, 검증 방법(시험/검사/분석/시연)을 가진다.
- 다른 요구사항과 충돌·중복이 없다.
- 구현 방법(how)이 아닌 요구(what)를 쓴다. 단, 제약사항은 예외.

권장 항목 표:

```
| ID | 구분 | 요구사항 | 출처 | 우선순위 | 검증 방법 | 상태 |
```

## 3. 품질 요구사항: ISO 25010 준수

품질 요구사항은 ISO/IEC 25010 제품 품질 모델의 특성·부특성 중 하나에 매핑하고, 요구사항에 매핑을 명시한다.

ISO/IEC 25010:2023 특성: 기능 적합성(Functional suitability), 성능 효율성(Performance efficiency), 호환성(Compatibility), 상호작용 능력(Interaction capability), 신뢰성(Reliability), 보안성(Security), 유지보수성(Maintainability), 유연성(Flexibility), 안전성(Safety).

> 2011판(사용성, 이식성 등 8개 특성)을 쓰는 프로젝트라면 해당 판을 `CLAUDE.md`에 명시하고 그 용어를 쓴다.

작성 규칙:
- 항목마다 `품질 특성 > 부특성`을 기재한다. 예: `신뢰성 > 복구성`.
- 정량 기준과 측정 조건을 반드시 쓴다. 예: "...전원 복구 후 2초 이내에 정상 상태로 복귀해야 한다."
- 적용하지 않는 특성은 문서에 "해당 없음 + 사유"로 남겨 누락과 구분한다.

## 4. 양방향 추적성 (필수)

모든 요구사항은 앞뒤로 추적 가능해야 한다.

- 상향(Backward): 요구사항 ← 이해관계자 요구/상위 시스템 요구
- 하향(Forward): 요구사항 → 아키텍처 요소(`ARCH-`) → 상세 설계(`DD-`) → 소스 코드 → 단위 테스트(`UT-`)
- 검증: 요구사항 → 시스템 테스트 케이스(`ST-`). **요구사항 커버리지 100%**(모든 요구사항에 시스템 테스트 케이스가 있어야 함)가 시스템 테스트의 합격 기준이다. 통합 테스트(`IT-`)는 아키텍처 인터페이스에서 추적한다.
- 추적 정보는 `docs/traceability/trace-matrix.md`에 둔다.
- 하향 링크가 없는 요구사항(미구현·미검증)과 상향 링크가 없는 설계/코드/테스트(근거 없는 항목)를 모두 찾아내 보고한다.
- 요구사항이 바뀌면 영향받는 하향 산출물을 목록으로 제시한다.

## 5. 절차

1. 입력 수집: 이해관계자 요구, 상위 문서, 기존 요구사항. 모호한 부분은 가정하지 말고 질문 목록으로 만든다.
2. 요구사항 도출 및 분류 (1절).
3. 품질 요구사항에 ISO 25010 매핑 (3절).
4. 안전 관련 항목을 식별해 별도 안전 문서로 분리 (1절).
5. 일관성·검증 가능성 점검 (2절).
6. 추적 매트릭스 작성·갱신 (4절).
7. `review` 스킬로 요구사항 체크리스트 리뷰를 수행한다. 리뷰 없이 확정하지 않는다.
